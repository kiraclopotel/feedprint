# Subsystem: i18n

> Traced from code. Confirmed defects live in the defect register `known-issues.md`, which is not part of the public copy; [KNOWN-LIMITS.md](../KNOWN-LIMITS.md) carries what a reader outside the project needs from it. Re-read against the code in the 2026-08-23 objective audit (spec-drift.md item 101).

## Purpose

Provides EN, ES, PT-BR and RO string tables for every FeelingWise UI surface (popup, dashboard, on-page marker, coverage map). Language is resolved once at each surface root from settings.uiLanguage ('auto' | 'en' | 'es' | 'pt-BR' | 'ro'); 'auto' delegates to navigator.language. The subsystem is the single authority for all user-visible static copy; AI-generated text (rewrites, explanations) is out of scope, and the HTML-export verifier keeps its own table, now typed against the same language set (`ExportLocale = ResolvedUiLanguage`).

Spanish and Brazilian Portuguese landed 2026-09-04 on the Chrome Web Store weekly-user split (Spanish 37%, Portuguese Brazil 11%, Romanian absent). Reference: docs/history/2026-09/LANGUAGES-SESSION-BRIEF-2026-09-04.md.

## Inputs

settings.uiLanguage ('auto'|'en'|'es'|'pt-BR'|'ro') read from chrome.storage at each surface root (Popup.tsx, the Off popup OffPopup.tsx, Dashboard.tsx content/index.ts); both popups carry the control that writes it (the Off row landed 2026-09-03, owner item 4 of the second live test). navigator.language is read inside resolveUiLanguage() as the fallback when pref is 'auto' (index.ts). The per-language PRETTY_TECHNIQUE_* and BLOCKED_CATEGORY_LABELS_* maps arrive from color-maps.ts at module-load time (dashboard-strings.ts). TechniqueName type (src/types/analysis.ts) gates MARKER_TITLES and MARKER_REASONS record keys.

## Outputs

ResolvedUiLanguage ('en'|'es'|'pt-BR'|'ro') passed to: (1) I18nProvider → usePopupT()/useDashboardT() hooks used by every React component in Popup.tsx and Dashboard.tsx and sub-components; (2) MARKER_STRINGS[lang], MARKER_TITLES[lang], MARKER_REASONS[lang] consumed by teen-marker.ts and injector.ts for on-page copy; (3) exportLocale (= useUiLanguage()) passed to buildForensicHtmlExport() and exportPDF() to select the HTML-export and PDF I18N tables.

## Invariants & contracts

- TypeScript interface contract: every key in PopupStrings/DashboardStrings/MarkerStrings/CoverageStrings must appear in EVERY language table — the Record<ResolvedUiLanguage, …> type makes both a missing language and a missing key a compile error, not a silent gap (popup-strings.ts dashboard-strings.ts marker-strings.ts coverage-map.ts)
- MARKER_TITLES and MARKER_REASONS are typed Readonly<Record<TechniqueName, string>> — every TechniqueName must map in every language or the build fails (marker-strings.ts)
- resolveUiLanguage() always returns a member of the shipped set — never undefined, empty string, or the raw 'auto' token (index.ts)
- Browser-tag matching is on the SUBTAG BOUNDARY, never a bare prefix: a language matches when the tag is it ('es') or a regional variant of it ('es-PE'). 'ru-RU' must not read as Romanian; that guard now covers 'esk' and 'ptx-XX' too (tests/unit/i18n/i18n.test.ts)
- Every Portuguese region, pt-PT included, resolves to the pt-BR table. It is written in Brazilian Portuguese and labelled that way; a European reader is far better served by it than by English (index.ts)
- Intl formatter tags come from intlLocaleFor(), never from an inline ternary. The old `lang === 'ro' ? 'ro-RO' : 'en-US'` pattern silently gave US formatting to every language added after it
- The image/video safety prompts stay EN/RO through mediaPromptLanguage(). Those prompts are instruments and are frozen (CLAUDE.md), so a Spanish or Portuguese parent reads a translated interface with English media evidence prose. Widening it means a new measurement, not a prompt edit
- String tables are module-level constants — they are never mutated after load; consumers read [lang] at render time, so a language change only needs to re-render the tree, not reload tables
- The per-language PRETTY_TECHNIQUE_* and BLOCKED_CATEGORY_LABELS_* maps are not typed to an interface — gaps silently fall back to EN in the techniqueLabel delegate chain: PRETTY_TECHNIQUE_<LANG>[id] ?? PRETTY_TECHNIQUE[id] ?? id (dashboard-strings.ts). tests/unit/ui/dashboard/components/technique-color-maps.test.ts asserts every TechniqueName resolves in every map
- Export locale equals the UI language at render time (ExportTab.tsx), and `ExportLocale = ResolvedUiLanguage`, so adding an interface language is a compile error in html-export.ts until its I18N table carries it — never a silent English fall-back inside a court-facing document. The signed forensic payload is untouched; locale selection is display-only

## How it SHOULD work

settings.uiLanguage is read once at each surface root. resolveUiLanguage maps it to one of the shipped languages (auto-detect from navigator.language). The resolved value is placed in I18nContext via I18nProvider. Every child component calls usePopupT() or useDashboardT(), which reads the context and returns the matching typed string table. On-page content scripts call resolveUiLanguage() directly (no React context) and pass the result into MARKER_STRINGS/TITLES/REASONS lookups. When the user changes uiLanguage in Settings, chrome.storage fires an onChanged event; both Popup (line 1240) and Dashboard (line 2101) re-read settings and update the resolved lang, causing a full re-render. The HTML export uses the same resolved lang for its embedded verifier I18N table.

## How it ACTUALLY works

Popup (Popup.tsx): resolveUiLanguage(settings?.uiLanguage) is called in the root render. Result passed to I18nProvider. All child components call usePopupT() → POPUP_STRINGS[useContext(I18nContext)] (react.tsx). The storage-change listener re-reads settings and triggers re-render. Dashboard (Dashboard.tsx): same pattern — resolveUiLanguage(settings.uiLanguage) → I18nProvider at lines 2165,2179. useDashboardT() used throughout. Content script (content/index.ts): resolveUiLanguage(settings.uiLanguage) called inline at every injection point — no context, direct MARKER_STRINGS/TITLES/REASONS[lang] access via teen-marker.ts and injector.ts. teen-marker.ts (lines 56-61, 122-127): getReasonFor() reads MARKER_REASONS[lang][technique] with fallback to MARKER_STRINGS[lang].fallbackReason. MARKER_TITLES[lang][technique] ?? MARKER_STRINGS[lang].patternDetected for the title. injector.ts reads MARKER_STRINGS[lang]. Export: Dashboard.tsx const exportLocale = useUiLanguage() passed to exporter buildForensicHtmlExport(); html-export.ts has its own I18N table keyed by ExportLocale (= ResolvedUiLanguage), separate from the four main string files; the embedded verifier script carries its own `LOCS` map for the ROOM labels and the Intl formatters, declared at the point `loc` is computed because `var` hoists the declaration and not the assignment. exporter.ts's PDF_STRINGS is keyed the same way and falls back per key to EN.

## Data flow (through this subsystem)

1. settings.uiLanguage ('auto'|'en'|'es'|'pt-BR'|'ro') read from chrome.storage (storage/settings.ts) -> resolveUiLanguage(pref, navigator.language) (index.ts) -> ResolvedUiLanguage ('en'|'es'|'pt-BR'|'ro')
2. ResolvedUiLanguage -> I18nProvider value prop (react.tsx) -> I18nContext (react.tsx)
3. I18nContext -> usePopupT() (react.tsx) -> POPUP_STRINGS[lang]: PopupStrings -> Popup.tsx components via t.*
4. I18nContext -> useDashboardT() (react.tsx) -> DASHBOARD_STRINGS[lang]: DashboardStrings -> Dashboard.tsx + ChainBanner + DashHeader + ExposureView and every other dashboard component via t.*
5. DASHBOARD_STRINGS[lang].techniqueLabel(id) -> PRETTY_TECHNIQUE_<LANG>[id] ?? PRETTY_TECHNIQUE[id] ?? id (dashboard-strings.ts) -> display string
6. settings.uiLanguage -> resolveUiLanguage() inline call (content/index.ts) -> lang: ResolvedUiLanguage -> passed to injectIntoElement / markOnlyElement / teen-marker functions
7. lang -> MARKER_STRINGS[lang]: MarkerStrings (teen-marker.ts injector.ts) -> on-page label strings
8. lang -> MARKER_TITLES[lang][technique] ?? MARKER_STRINGS[lang].patternDetected (teen-marker.ts) -> marker title on social page
9. lang -> MARKER_REASONS[lang][technique] ?? MARKER_STRINGS[lang].fallbackReason (teen-marker.ts) -> yellow-state reason text on social page
11. useUiLanguage() -> exportLocale: ExportLocale (ExportTab.tsx) -> buildForensicHtmlExport(opts with locale) / exportPDF(records, locale) (exporter.ts) -> html-export.ts I18N[locale] and exporter.ts PDF_STRINGS[locale] -> embedded verifier and PDF copy

## Resolved (kept as the fix record; commits in git log)

- **[was high] PRETTY_TECHNIQUE / PRETTY_TECHNIQUE_RO / TECHNIQUE_COLORS now keyed by the full TechniqueName enum.** Previously these maps used 13 short legacy ids (parasocial, consumer-rapid, hyperreal-trauma + the 10 base techniques), so 11 of the 21 TechniqueName values missed the lookup — the dashboard techniqueLabel delegate returned the raw kebab-case id and dots defaulted to grey. The three youth ids were re-keyed to their enum names (parasocial-coercion, consumer-rapid-frame, hyperreal-trauma-bait) and the 8 absent techniques (profanity, body-comparison-priming, combined-stack, sexual, violence-graphic, self-harm, drug-promotion, extreme-toxicity) were added with EN+RO labels and colors. Existing correct labels were kept. Display-only change: keys feed the techniqueLabel delegate and the click-filter/color lookups, not the signed forensic payload, so no hash drift. Guarded by tests/unit/ui/dashboard/components/technique-color-maps.test.ts, which asserts every TechniqueName resolves to a non-kebab label and a hex color, and that the stale short keys are gone. — src/ui/dashboard/components/color-maps.ts

- **Spanish and Brazilian Portuguese added to the interface (2026-09-04).** The product shipped EN and RO while the store's weekly-user split read Spanish 37% (Peru), Portuguese Brazil 11%, Romanian absent. `ResolvedUiLanguage` now carries four languages and one roster, `UI_LANGUAGES`, that both product pickers and every parity test read, so a fifth language is one table per surface plus one roster line. Three latent bugs fell out of the widening rather than being hunted: the Intl ternaries would have given US formatting to Spanish and Portuguese (now `intlLocaleFor`), the export locale would have silently fallen back to English inside a court-facing document (now `ExportLocale = ResolvedUiLanguage`, a compile error), and the inline verifier's locale pick would have done the same (now a `LOCS` map). Not touched by this pass: the adult text judge and the image/video prompts, both frozen instruments. The fixed swear/slur lists were left too, and the filters session extended them to Spanish and Portuguese the same afternoon (f3a78a0, 0626bc0); note that its region gate reads `navigator.language`, not `settings.uiLanguage`, so the picker and the word list answer to different inputs on purpose. — src/i18n/, src/forensics/html-export.ts, src/ui/dashboard/components/color-maps.ts
