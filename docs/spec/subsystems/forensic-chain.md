## Purpose

Maintains an append-only, hash-linked local observation chain for content observations FeelingWise processed (flagged, pass, skipped, cancelled, blocked, environment, manual-flag, reset/rotation markers). Every record is SHA-256 hashed over a canonical payload. New active-chain writes require a stamped per-install fingerprint and an ECDSA P-256 signature: persistent identity/signing failure leaves automatic observations in the durable outbox instead of storing weaker evidence. Historical unsigned records remain immutable and visible as amber/unverified. Records are stored in IndexedDB compressed via gzip. A standalone HTML export embeds an offline Web Crypto checker for stored hashes, chain links, and signatures under the public key embedded in that file. The checker derives the fingerprint from the JWK and rejects a different declared label. Green requires every included signature to verify; missing/different-key signatures are amber/unverified, and hash/link/current-key signature failures are red. Because the key travels inside the file, this check does not independently establish key identity, platform origin, or completeness.

## Inputs

Detection pipeline sends FORENSIC_LOG / PASS_LOG / CANCEL_LOG / BLOCKED_LOG / ENVIRONMENT_LOG with a stable delivery ID through content/forensic-retry.ts to service-worker.ts. Comment-batch cancellation inputs may carry optional roomAuthor / roomCaption / roomUrl; logCancelEvent preserves them on the signed record, while undefined legacy/non-comment inputs remain hash-compatible through canonical omission. Dashboard sends RESET_FORENSIC_CHAIN, GET_SIGNING_METADATA, and RESTORE_FORENSIC_BACKUP messages, each carrying the parent PIN that the service worker verifies at its boundary (no PIN, no configured PIN, or a wrong PIN is refused; the 15-minute popup grace window is ignored here). MANUAL_FLAG has a SW handler, a message type and a unit test but no sender under src/ui (the `.manual-flag-form` CSS has no JSX), so the manual-flag backend is currently unreachable from any surface. The service worker owns automatic delivery, signing-key first use, reset, and restore in its single chain-write realm.

## Outputs

ForensicRecord objects written to IDB (feelingwise-forensics, store=records, v6) as CompressedRecordEnvelope. The same DB holds deliveryOutbox, deliveryReceipts, and deliveryMeta stores. ChainAnchor rows are written to the chainAnchors sidecar; monthly archives use feelingwise-forensics-YYYY-MM DBs. JSON backup files, standalone HTML exports, integrity results, and durable-delivery status are returned to their dashboard/export consumers.

## Q82 design, RATIFIED 2026-08-11 (NOT YET IMPLEMENTED): prune-marker-attested gap

Problem: the FIFO cap prune deletes by lowest IDB key, so on a 10k+ rotated month the
month-rotation marker (chainPosition 0) is deleted first, severing the chain-of-chains
priorChainHash link. The naive fix (exempt the marker from the prune cursor) was implemented
and reverted: keeping position 0 while deleting 1..N creates an interior gap and the
DASHBOARD walker (chain-integrity.ts verifyChainIntegrity) fails it as position-mismatch.

Finding that reshapes the fix (verified in code 2026-08-11): the embedded HTML-export verifier
is ALREADY gap-tolerant by design (html-export.ts verifyChain enforced links only on contiguous
chainPositions, for filtered exports; since 2026-09-03 it resolves every link as a hash across
the whole file, see the html-export.ts entry above); the strict contiguity constraint lives ONLY in the
dashboard walker and the structural restore walk that share verifyChainIntegrity. The prune
marker already attests everything needed, signature-covered: deleted count + position range
inside canonical-hashed originalText, and priorChainHash = the newest deleted record's
integrityHash (canonical-payload.ts includes priorChainHash).

Ratified rule, one gap, fully attested. verifyChainIntegrity accepts a single interior gap iff
ALL of:
1. chainRecords[0] is kind='month-rotation-marker' at chainPosition 0 (the exempted marker);
2. the gap sits immediately after it: chainRecords[1].chainPosition = G+1 where positions
   1..G are absent;
3. a kind='prune-marker' record later in the same chain attests, in its hashed originalText
   range, firstDeletedPos=1 and lastDeletedPos=G (repeated prunes: the newest marker's range
   must end at G; earlier markers cover earlier sub-ranges);
4. chainRecords[1].prevRecordHash === that prune marker's priorChainHash (the survivor
   cryptographically links to the newest deleted record the marker attests).
On acceptance the walk resumes at chainRecords[1] with expectedPrevHash taken from the record
itself; every other rule is unchanged. Any unattested gap stays position-mismatch. The incremental verify
watermark refuses on any prune (shape movement) and falls back to the full walk, unchanged.

Implementation (one commit, cross-month tests mandatory): (a) prune cursor exempts a
position-0 month-rotation-marker; (b) the walker gains the four-condition rule above; (c) the
embedded verifier needs no link change but must keep rendering the prune marker as a marker
line so the gap is named, not silent; (d) tests: pruned-rotated-month verifies valid with the
month link intact, unattested gap still fails, forged range fails condition 4, repeated prunes.
Gate: implement when a month actually approaches the 10k cap (live-volume gate) or
alongside the next verifier-touching work, whichever first.

## How it SHOULD work

On every post observation, logger.ts acquires sharedChainWriteLock, calls getChainState() to get the next chainPosition and the previous record's integrityHash, builds the ForensicRecord partial, stamps the publicKeyFingerprint, feeds the whole partial to computeRecordIntegrityHash() (canonical JSON.stringify → SHA-256), then calls addRecord() which signs the hash with ECDSA P-256 and writes a gzip-compressed envelope to IDB. The chain is hash-linked and the ECDSA signature covers the canonical content plus link. verifyChainIntegrity() walks positions, hashes, links, and current-key signatures. `IntegrityResult.valid` means no detected break; presentation uses `integrityVerificationState()` so unsigned, prior-key, pre-rekey, and pre-chain records produce amber/partial rather than green. Backup/restore preserves signatures verbatim without asserting that unavailable earlier keys verified. The HTML export applies the same three-state rule: VERIFIED only when every signature verifies under the embedded key; PARTIALLY VERIFIED for internally consistent records whose signing key is unavailable; FAILED for hash/link or matching-key signature failure.

## How it ACTUALLY works

DELIVERY: every FORENSIC_LOG, BLOCKED_LOG, PASS_LOG, CANCEL_LOG, and ENVIRONMENT_LOG receives a stable delivery ID and capture timestamp before its first send. The service worker validates both, consults persisted epoch fences, and commits either the payload or a final discarded receipt under the chain lock before acknowledging. One SW-realm pump drains all tabs by durable auto-increment sequence, so same-millisecond captures cannot reorder by random ID. A successful write atomically adds the signed record with its original capture time, deletes the outbox row, and adds a committed receipt; the receipt makes a lost acknowledgement safe to replay. A failure persists attempts, error text, and a bounded next-attempt time, then stops the pump so later records cannot overtake it; the eighth failure quarantines the row and the pump continues past it. Worker import, a one-minute alarm, a retry timer, and every new pending enqueue kick recovery. The content-realm 20-entry/three-attempt buffer covers explicit failures and ambiguous live-context transport failures. The Issues tab shows pending/unreadable state and recent restore exclusions.

WRITE + SIGNING: logger.ts acquires the SW-realm `sharedChainWriteLock`, reads the largest active chain position, builds the record, stamps the public-key fingerprint, and computes the canonical SHA-256 hash. `addRecord()` signs immediately, then after 100 ms and 500 ms. Exhaustion rejects before compression or IndexedDB. A successful signature is gzip-wrapped and added to the records store. `getChainState()` returns genesis only after a successful empty read; an IDB error throws. `readStoredKeys()` generates a new identity only after a successful read finds all stored key fields absent; read errors and partial key state throw. Historical unsigned/restored rows remain immutable and amber.

VERIFICATION: `verifyChainIntegrity()` filters the active chain, checks position, previous hash, recomputed canonical hash, and signature state. The dashboard runs the full walk once per load and on manual Verify (cross-month on manual Verify); its passive refreshes (visibility, focus, settle) drop the verdict and call `extendChainIntegrity()` from the last watermark, which walks only the appended records and falls back to the full walk when the prefix shape moved. A missing signature or unavailable different key is amber/partial; only a failed signature whose record fingerprint matches the current key is red `key-mismatch`. Dashboard verification is read-only. The HTML verifier derives the fingerprint from its embedded JWK, rejects a different declared fingerprint, catches malformed input, and applies the same verified/partial/failed rule. Relegation changes only `chainAnchor`; the one-shot auto-heal path repairs hash-proven historical positions and never authenticates unavailable signatures.

ROTATION: `rotateChainAtMonthFlip()` runs entirely under the SW-realm chain lock and defers while the outbox is nonempty. It snapshots and verifies the active source, prepares a signed marker before storage mutation, and either verifies/copies the archive or resumes from an archive whose every payload hash recomputes, whose chain verifies, and whose ordered id/position/hash/signature/anchor descriptors exactly match the source. Active clear + marker add + rotation cutoff are one IDB transaction. A capture from before that boundary which was still waiting to enqueue is retained in the new active chain with signed `late-after-rotation:*` provenance; the marker, not that older record timestamp, remains the epoch-month authority. Any preparation, archive, or cutover failure leaves the active source intact.

RESET: the dashboard sends RESET_FORENSIC_CHAIN with the parent PIN to the service worker, which verifies the PIN before anything else (invariant 14); the dashboard modal reads the typed `errorKind` so a wrong PIN, a reset failure and a lost response render three different states (`reset-modal-status.ts`). Under the same SW-realm chain lock, reset reads the prior terminal fail-closed, prepares a signed Reset Marker, and atomically replaces the active rows with that marker. In the same transaction it converts every pending outbox delivery to a `discarded-reset` receipt, clears the outbox, and publishes the marker capture-time boundary, so a stale content-script replay cannot resurrect pre-reset evidence. The per-install signing identity is retained. After cutover it clears processing caches and the scan/author/verdict/diagnostic/usage/feedback/anchor sidecars. Read, signing, compression, or cutover failure rejects instead of erasing the source.

BACKUP + EXPORT: `buildBackupBlob()` includes records, anchors, feedback, and public-key material. Automatic backup captures records and identity under the SW chain lock, then performs download I/O after release; automatic and safety backups are passphrase-sealed through `backup-envelope.ts`, a folder-wired silent mirror (`backup-folder-wire.ts`) writes beside the download when the parent has granted a folder, and a pre-restore safety copy is written before any restore (invariant 10b). Restore requires the parent PIN (verified by the SW like reset) and a confirm-on-replace step in the Export tab. Restore refuses a nonempty outbox, saves outgoing evidence under its original identity, decrypts/validates a wrapped key without persisting it, requires it to match the backup JWK/fingerprint, then atomically replaces records+anchors+parent feedback, clears outgoing receipts, and publishes a destructive capture-time cutoff. A late pre-restore arrival is excluded and counted in Issues rather than being signed under the imported identity. Only after the swap may the staged key commit. HTML export uses the drift-tested canonical-payload mirror. TSA calls run outside the lock, but the returned anchor is committed only after the same head revalidates under it.

FILTERED EXPORTS: JSON/CSV/PDF export filtering treats `minOverallScore` as a severity floor over `overallScore`. The wrapped JSON export exposes `below_severity_threshold` for that count and keeps `low_confidence` as a legacy alias for older consumers. CSV includes `mode_at_capture`, derived from signed `configSnapshot.mode` when valid and otherwise from signed `userAgeCategory`; PDF shows the same value per record. CSV also carries `config_video_understanding` and `config_image_understanding`, empty when the record does not state them; the PDF/HTML report renders the same two states in plain language in every interface language, and prints nothing when they are absent. Standalone HTML export copy is mode-neutral because one export can contain child, teen, and adult records.

## Data flow (through this subsystem)

1. Content script creates a stable deliveryId and sends an automatic record message through sendHighStakesForensicLog().
2. The service worker validates the ID, commits the payload to deliveryOutbox, then acknowledges `{ok:true,state:'pending'}` and kicks the pump.
3. The single-flight pump reads the oldest outbox row and dispatches it to the matching logger.
4. The logger enters sharedChainWriteLock, reads chain state, stamps the required public-key fingerprint, computes the canonical integrity hash, and calls addRecord(record, deliveryId).
5. addRecord retries ECDSA signing at 0/100/500 ms and compresses the exact signed value before opening the write transaction.
6. One v6 IDB transaction adds the record, deletes deliveryOutbox[deliveryId], and adds a unique committed deliveryReceipts[deliveryId]. Transaction failure rolls all three operations back.
7. The pump continues FIFO. On failure it persists attempt/error/backoff on the same outbox row, stops, and schedules the next kick; after 8 attempts the row is quarantined and the pump continues.
8. Dashboard verification reads/decompresses records and applies verifyChainIntegrity(); Issues independently reads getForensicDeliveryStatus() so pending evidence is never silent.
9. Dashboard export builds the standalone HTML verifier; its inline canonical hash, chain-link, fingerprint, and ECDSA checks run without a server.
