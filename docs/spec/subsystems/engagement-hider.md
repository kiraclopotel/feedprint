# Subsystem: engagement-hider

> Traced from code. Confirmed defects live in the defect register `known-issues.md`, which is not part of the public copy; [KNOWN-LIMITS.md](../KNOWN-LIMITS.md) carries what a reader outside the project needs from it. Re-read against the code in the 2026-08-23 objective audit (spec-drift.md items 67 to 72).

## Purpose

Performs on-page DOM protection across five platforms: hides engagement metrics (like/view/share counts), action buttons, comment input composers, and whole surfaces (Reels/Shorts, AI-labeled content, sidebar ads, X textless sponsored articles). All hiding is pure CSS + inline-style DOM mutation — no AI calls, no network, no chrome.storage write per tick. Settings are read once at start; runtime toggle changes trigger full teardown → DOM reset → restart via a chrome.storage listener in the controller.

Scheduling (2026-09-03): inserted subtrees are handed to every incremental scanner by ONE shared body observer (`added-roots.ts`) synchronously inside the mutation callback, so a hide lands before the element's first paint; each module keeps a 2 s full pass as the safety net for text the platform swaps into an existing node. The bounded-selector platform sweeps (TikTok, X, YouTube, the AI blocker) run behind a TRAILING 750 ms throttle that never drops a call. Measured with `scripts/verify/engagement-latency.mjs` (real Chromium, the built Off, a 28k-node Facebook-shaped fixture served in place of facebook.com, everything on): insert-to-hide p50 went from 426 ms (bars) / 113 ms (words) / 1.4 s (reply prompts, max 2.0 s) to 20 ms each, and main-thread long tasks while 20 posts arrived from 18 tasks / 3.3 s to 3 tasks / 0.18 s. Run the instrument with the tab in the FOREGROUND: a background tab pauses rAF and the same measurement read 770 ms for a 30 ms path.

## Inputs

Platform string (resolved in content/index.ts at adapter init) enters initEngagementControl(), which content/index.ts calls once; the master cleanup the controller returns is discarded at that call site (`initEngagementControl(platform).catch(...)`), so nothing but context death removes the controller's storage listener. FWSettings (from chrome.storage via getSettings()) carries the feature-flag map (hide-engagement-metrics, hide-action-buttons, block-comment-posting, strip-emojis, block-ai-content, block-reels, media-timeout, block-ads, rewritten-comments-first) with per-platform override support. Runtime changes arrive via chrome.storage.onChanged. The AI-content blocker also reads BlockAiContentValue.hashtags from getFeatureValue(); media-timeout reads its optional `{ schedule }` payload the same way. Because the controller restarts on any `features` change, editing a schedule in the popup takes effect without a reload.

## Outputs

Pure DOM mutations: injected <style> tags, inline display/visibility/pointer-events overrides, data attribute markers on affected elements. Counters: mark-hidden.ts batches the hides and calls incrementMetricsHidden(n) once per second, which writes to chrome.storage (popup ASCUNSE column). Callers fire it as `void`, so overlapping calls are normal; settings.ts serialises the read-modify-write through one shared chain (`serializeCounterWrite`, shared with incrementChecks and incrementNeutralized) so overlapping increments are not lost. Do not remove that serialisation to "await less": awaiting at the call sites would block a paint on storage. KNOWN RESIDUAL: the chain is module state and therefore per-realm, so two TABS incrementing at the same instant can still lose one; closing that needs the read-modify-write moved behind the service worker. Forensic writes: BLOCKED_LOG messages to SW via safeSendMessage() (reels-blocker, ai-content-blocker, media-timeout). dataset.fwProcessed='true' stamped on blocked containers to pre-empt the platform extraction pipeline.

## How it SHOULD work

Parent configures feature toggles (per-mode presets or individual switches). On page load, content/index.ts resolves the platform and calls initEngagementControl(platform). Controller reads settings, calls shouldControlEngagement(), and if any relevant toggle is on calls startPlatformEngagement(). That starts seven parallel modules (emoji-stripper, empty-comment-hider, ai-content-blocker, reels-blocker, media-timeout, sidebar-ad-blocker, media-only-ad-blocker) plus the platform-specific adapter (TT/X/IG/FB/YT). The incremental modules (structural finder, section model, word filter, emoji stripper, empty-comment hider, the FB reply-prompt hider) receive inserted subtrees from the shared added-roots observer and hide before paint; the bounded-selector platform sweeps run behind a trailing 750 ms throttle on the rAF observer; every module keeps a 2 s full pass for content swapped in place; all stamp markers + inline styles. When settings change, the controller tears everything down, resets the DOM, and restarts with fresh settings. Each module returns a cleanup function; the master cleanup calls all of them.

## How it ACTUALLY works

controller.ts initEngagementControl() is called async from content/index.ts; reads settings via getSettings() (chrome.storage); calls shouldControlEngagement() against 9 feature flags. If true, calls startPlatformEngagement(). The returned master cleanup is never stored or called by its one caller.

startPlatformEngagement() (controller.ts) fires 7 parallel starts unconditionally (subject only to each module's own isFeatureEnabled gate): emoji stripper, empty-comment hider, ai-content blocker, reels blocker, media timeout, sidebar ad blocker, media-only ad blocker; then switches on platform to start the platform adapter. Returns a composite cleanup.

3. FWSettings -> isFeatureEnabled(settings, 'hide-action-buttons' | 'hide-engagement-metrics' | ..., platform) (settings.ts) -> boolean per feature per platform
4. ## Resolved (kept as the fix record; commits in git log)

- **H8** — TikTok + Twitter engagement body observers are now wrapped in createRafBodyObserver() with a 750ms minimum-interval throttle (RUN_THROTTLE_MS), mirroring youtube-engagement.ts. Each module now runs a single rAF-debounced + throttled body observer driving a `*Throttled` sweep wrapper; the immediate-start sweep, the 2s setInterval coverage (calls the un-throttled sweep directly), and the teardown/cleanup are preserved. This removes the un-debounced full-DOM-scan-per-mutation pattern that OOM'd YouTube. Hiding behavior (what gets hidden) is unchanged. — src/content/engagement/tiktok-engagement.ts:356, src/content/engagement/twitter-engagement.ts:218 (test: tests/unit/storage/engagement-observer-throttle.test.ts)
- **M27** — ai-content-blocker.ts:resetDOM() now UNMUTES media on toggle-off. blockContainer() records each muted container in a module-level `blockedContainers` Set (parallel to mediaObservers); resetDOM iterates it and runs unmuteAllMediaIn() (sets media.muted=false; does NOT call play()) before clearing the Set. A video already on screen when the parent turns off block-ai-content is no longer left silent until the next swipe/reload.
