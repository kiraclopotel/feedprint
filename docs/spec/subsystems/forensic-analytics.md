# Subsystem: forensic-analytics

> Traced from code. Confirmed defects live in the defect register `known-issues.md`, which is not part of the public copy; [KNOWN-LIMITS.md](../KNOWN-LIMITS.md) carries what a reader outside the project needs from it. Re-read against the code in the 2026-08-23 objective audit (spec-drift.md items 89, 90).

## Purpose

Derives interpretive views over the signed forensic chain (ForensicRecord[]) for the dashboard Patterns and Statistics tabs. Covers: TF-IDF topic fingerprinting and theme clustering (topics.ts), two theme queries (themes.ts), theme sidecar cache in a separate IDB (theme-cache.ts), re-serve / exact-repeat detection (reserve.ts), exposure timeline / amplification / author escalation / evidence rollup (analytics.ts), record-sequence structure analytics including skew, periodicity, runs, and narrative-pressure signals (sequence.ts), scan-log denominator tracking (scan-log.ts + scan-activity.ts), integrity summary reduction (integrity-summary.ts), chain debug stats and operational event bucketing (chain-debug-stats.ts), per-author entity store (author-store.ts), neutralizer diagnostics counter (neutralizer-diagnostics.ts), and two dev-gated prompt/behavior capture stores (capture-prompt-io.ts, capture-behavior.ts). All pure analytics paths are deterministic and recomputable from the chain without re-running the AI pipeline.

A group is one author (case-folded) and one key with 2 or more distinct `originalHash` values and 2 or more sittings under the exact panel's 30-minute rule; a group with one hash is the exact panel's case and is skipped, so the two counts never overlap. Same provenance fields plus `variants` (distinct hashes) and `templateKey`. Rendered as "Observed again: the same item with the numbers changed" in Patterns, through the same row component. Lock: tests/unit/forensics/reserve-template.test.ts, with a two-sided ACCEPT/REJECT corpus for the key.
- src/forensics/platform-switch.ts - `computePlatformSwitches(records)` since 2026-09-06 (capability audit P1 item 6): the first cross-platform number the record supports with no new field. A switch is two consecutive content records in timestamp order on different platforms inside one sitting (gap under 30 minutes, the Activity divider rule); a sitting boundary is never a switch. The after-switch window is the first 5 content records on the new platform, cut by the next switch or the sitting boundary; the baseline is every content record outside a window; the two partition the pool. Content and flag rule as the Statistics balance bar. Both shares carry k, n and the Wilson interval; pairs are counted by direction. Rendered as the "After a platform switch" panel in Patterns, over the windowed chain. Claims nothing about serve order or intent. Lock: tests/unit/forensics/platform-switch.test.ts.
- src/forensics/wilson.ts - `wilson(k, n)`: the one helper behind every printed share since 2026-09-06 (capability audit P0 item 2). Takes counts, never a rate; returns k, n, p and the 95% Wilson interval, plus rounded percentages, or null when n is 0 so the empty case is rendered on purpose. Same arithmetic as the research lane's `wilsonInterval` in scripts/research/lib/harness-common.ts. Used by StatisticsTab (balance line, severity bands, top technique shares with the axis's own counts, calibration agreement), OverviewTab (balance headline, day tips, per-surface flag rate) and the export's page one. Lock: tests/unit/forensics/wilson.test.ts.

## Invariants & contracts

- Two day-bucketing conventions, both deliberate (ruling 2026-08-11): parent-perception surfaces bucket by LOCAL midnight (StatisticsTab 14-day bars, its "today" tiles, overview-data dayKeyOf) because "today" must mean the parent's today; interpretation-engine aggregations bucket by UTC (computeExposureTimeline, computePeriodicity, computeRuns via orderedExposure) because exported evidence must reproduce identically on any verifier's machine (Promise 1). Consequence: near-midnight records can land on different days in the two families; the surfaces answer different questions and their bars must never be compared one-to-one. Do not "unify" this without re-reading this ruling.

- System markers never read as feed content (2026-08-11): every parent-facing aggregation excludes reset/rotation/prune markers through the single shared predicate `isSystemMarkerRecord` (`src/forensics/system-records.ts`) — theme eligibility (topics.ts), feed-composition's honest denominator, overview-data isBalanceContent, Dashboard platform rails and ledger sweeps, StatisticsTab balance pool, FeedCard marker rendering. The exported HTML verifier cannot import the predicate (embedded JS in template strings); its six marker lists carry all three kinds and a test locks their parity (system-marker-exclusion.test.ts). Any new aggregation must use the predicate, and the source-lock fails on a copy-pasted exclusion chain.
- topics.ts — TOPICS_ALGO_VERSION=1 must be bumped whenever tokenization, weighting, or threshold constants change; theme-cache reads compare this version and return null (force recompute) on mismatch
- topics.ts — buildFingerprints sorts corpus by (timestamp asc, id asc) before any processing to guarantee deterministic output regardless of input order
- topics.ts — theme.id is sha256 of sorted top-5 centroid term strings; must remain stable across recomputes for the same input set
- theme-cache.ts — chainFingerprint = '{count}:{lastId}:{lastTimestamp}'; any record add/remove/reset changes this and invalidates the cache
- theme-cache.ts — cache is only valid when BOTH algoVersion === TOPICS_ALGO_VERSION AND chainFingerprint matches; partial match is a miss
- analytics.ts — isExposureRecord: verdict==='flagged' || verdict==='flagged-hidden' || verdict===undefined; every exposure-oriented aggregation gates on this; must stay consistent with store.ts computeStats()
- analytics.ts — severityWeight reads verbatim from signed record, no re-scoring; the chain's integrity is the proof
- sequence.ts — orderedExposure() is the shared sort/filter for all order-sensitive sequence functions; any change propagates to computeRuns, computeExposureSkew
- sequence.ts:computeNarrativePressureSignals returns one independent result per platform and deliberately has no all-platform rollup. Motifs prefer the buildThemes assignment when supplied, then fall back to dominant technique, then feedSource; this keeps theme threads separate from platform capture logic.
- scan-activity.ts — PROTECTIVE_ACTIONS set is the authoritative definition of 'actedOn'; cancelled stays separate. reserve.ts SESSION_GAP_MS is 30 min, the same gap the dashboard's SESSION_GAP_MIN uses
- neutralizer-diagnostics.ts — todayKey() uses UTC, the same convention as settings.ts utcDayKey, so the diagnostic counter and the pipeline cap reset at the same instant

## How it SHOULD work

On Patterns tab open: load all ForensicRecord[] from chain, window to 7 or 28 days, check sidecar cache (theme-cache, IDB 'feelingwise-derived'), serve themes immediately if valid, else run buildThemes (fingerprint→cluster→theme assembly) deterministically, write result to sidecar, render predominant + cross-day themes + re-serve detections. On Statistics tab open: run pure analytics (timeline, amplification, author escalation, evidence rollup, skew, runs, periodicity) directly over ForensicRecord[], combine with AuthorProfile[] for escalation view. Scan-log provides the denominator (total scanned) vs numerator (actedOn). Integrity summary consumes the already-walked IntegrityResult from chain-integrity.ts. Dev-flag-gated capture stores write prompt I/O and queue lifecycle events for corpus building when flags are on; they never break the production path.

## How it ACTUALLY works

topics.ts:buildThemes: (1) filter eligible records (verdict in {flagged,flagged-hidden,pass,blocked} and non-empty text), (2) sort corpus by (timestamp,id), (3) pass-1 compute DF and surface-vote maps, (4) pass-2 per-record TF-IDF with entity-kind boost ×2 and top-12 selection, (5) greedy single-pass cluster via inverted index + cosine similarity threshold JOIN_SIMILARITY=0.35 (topics.ts), (6) merge sweep limited to clusters sharing a top-5 centroid term, MERGE_SIMILARITY=0.5 (topics.ts), (7) drop clusters below MIN_THEME_SIZE=3 (topics.ts), (8) async themeFromCluster: sha256 of sorted top-5 folded terms → 16-char hex id, label = top-3 surface forms joined by ' · ' (topics.ts). PatternsTab.tsx:86-105: reads from sidecar cache first (readThemeCache), falls back to buildThemes, writes result back. themes.ts predominantThemes: sort by recordCount desc then daysActive then id. themes.ts crossDayThemes: filter themes where daysActive >= 3. reserve.ts computeReservePatterns: group by originalHash, count distinct sessions by 30-min gap, filter minSessions>=2. sequence.ts computeExposureSkew: per exposure record, dominant technique (highest severity, first wins) + feedSource distribution → KL divergence from uniform. sequence.ts computePeriodicity: per-day severity-weighted series, zero-fill gaps, ACF at lags 1-14, detect local maxima >= 0.3. sequence.ts computeRuns: walk orderedExposure twice (technique runs, high-severity runs), merge, sort by length desc. scan-log.ts logScanEvent: opens new IDB connection per call (openDB does NOT use module-level singleton, unlike theme-cache.ts), closes after tx. scan-activity.ts summarizeScanActivity: pure over ScanEvent[], separates cancelled from actedOn (fixes the scan-log.ts computeScanStats conflation bug). author-store.ts updateAuthorProfile: IDB put-upsert keyed by the composite `profileKey` (handle@platform via authorProfileKey()); the same handle on two platforms is two distinct profiles (M18 fix; DB_VERSION 2 drops+rebuilds the v1 handle-keyed store). neutralizer-diagnostics.ts: writes to chrome.storage.local, NOT IDB; auto-resets on UTC day flip.

computeNarrativePressureSignals (sequence.ts) groups exposure records by platform, then derives escalation trajectory, rolling Shannon entropy drop, quiet-gap returns, and trigger-switch rate per platform. It uses theme assignment/labels when PatternsTab supplies them and never blends platforms into a single score.

2. windowed ForensicRecord[] -> readThemeCache(windowed) (theme-cache.ts) -> ThemeCacheEntry | null
3. on cache miss: windowed ForensicRecord[] -> buildThemes(windowed) (topics.ts) -> buildFingerprints (topics.ts) -> {fingerprints: RecordFingerprint[], surfaceForms: Map<string,string>}
4. RecordFingerprint[] -> clusterFingerprints (topics.ts) -> Cluster[] (greedy agglomeration via cosine + inverted index)
5. Cluster[] (filtered MIN_THEME_SIZE>=3) -> themeFromCluster (topics.ts) [sha256 theme id via hasher.ts] -> Theme[]
6. Theme[] + assignment Map -> writeThemeCache (theme-cache.ts) -> IDB 'feelingwise-derived' object store 'cache'
7. Theme[] -> predominantThemes (themes.ts) -> top-8 Theme[] for Patterns tab top section
8. Theme[] -> crossDayThemes (themes.ts) -> Theme[] with daysActive>=3 for recurring section
9. windowed ForensicRecord[] -> computeReservePatterns (reserve.ts) -> ReserveInstance[] (grouped by originalHash, filtered minSessions>=2)

9c. windowed ForensicRecord[] + assignment Map + theme labels -> computeNarrativePressureSignals (sequence.ts) -> NarrativePressureSignals (per-platform escalation / entropy collapse / quiet-gap return / trigger-volatility panel)

11. ForensicRecord[] -> computeAmplificationTrend (analytics.ts) -> AmplificationTrend (amplification labels + views/likes ratio + repeatedPosts)
12. ForensicRecord[] + AuthorProfile[] -> computeAuthorEscalation (analytics.ts) -> AuthorEscalation[] (flagRate + severity trend + escalating boolean)
13. ForensicRecord[] -> data-layer/index.ts periodWindow + aggregateBy* + comparePeriods -> ExposureView period panels
14. ForensicRecord[] -> computeExposureSkew (sequence.ts) -> ExposureSkew (KL divergence from uniform over technique + feedSource)
15. ForensicRecord[] -> computePeriodicity (sequence.ts) -> PeriodicityResult (ACF at lags 1-14, peak lags)
16. ForensicRecord[] -> computeRuns (sequence.ts) -> SequenceRun[] (technique streaks + high-severity streaks, length>=2)
17. pipeline result -> logScanEvent(event) (scan-log.ts) -> IDB 'feelingwise-scans' store 'events'
18. IDB 'feelingwise-scans' -> getScanEvents() (scan-log.ts) -> ScanEvent[] -> summarizeScanActivity (scan-activity.ts) -> ScanActivitySummary

(author-store.ts) -> extension-origin IDB 'feelingwise-authors' put-upsert. day (UTC YYYY-MM-DD) and textHash (creativeHash of the post body) are stamped by result-apply.ts on every processed post including cache hits, and feed the exposure counters; both optional, so a sender that omits them updates the flag counts only
